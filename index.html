Zero

Debt-payoff planning that runs on your own device. No servers, no accounts, no copies.

Zero computes the payment to make against each debt in a given month so the whole balance clears as early as possible, and states what that approach costs in interest compared with paying minimums. It is desktop software, licensed per household and run locally.

Architecture

Zero is single-tenant by design. Each installation runs on one device, serves one household, and holds only that household's data. There is no multi-tenant database, because there is no database outside the device. There is no Zero service to sign in to.

This is a deliberate position rather than a limitation: financial data that is never centralised cannot be exposed by centralised failure.

Why Zero requests account data

A payoff plan is only as accurate as the figures behind it, and the figures that drive it change without notice. Zero can read them from the accounts the user connects:

  • Balances — the amount actually outstanding.
  • Interest rates, minimum payments and due dates — the inputs the plan is computed from. A rate change that goes unnoticed re-orders the entire schedule.
  • Transactions — so that spending analysis and the short-term cash forecast are measured rather than estimated.

Account connections are made through Plaid, which retrieves the data from the institution on the user's behalf. The user authenticates on their institution's own page; Zero neither hosts nor scripts that page and never receives banking credentials. Plaid's handling of that information is governed by their end user privacy policy.

What Zero does not do

  • It does not move money. No transfers, no payments, no trades. Zero produces payment instructions; the user executes them.
  • It operates no servers. Data is stored on the user's device and transmitted nowhere. No account, no cloud copy, no analytics, no telemetry.
  • It does not store banking credentials. Access tokens issued by Plaid are held in the operating system's credential store.

Security

  • The application binds to the local loopback interface only, and that address is fixed at build time rather than configurable — so it cannot be exposed to a network by misconfiguration.
  • Stored data is encrypted with a key derived from the user's passphrase, which is not retained anywhere. Until the application is unlocked it cannot read its own files, and neither can any other process on the device.
  • Access requires two factors: that passphrase and a time-based one-time code. No data is served and no institution can be connected until both are configured.
  • A single command revokes every institution connection at the aggregator and deletes all local data — the connection is revoked, not merely forgotten.
  • Dependencies are checked against a public vulnerability advisory database daily, and an outstanding advisory fails the build.

Further detail is in the privacy policy. An information security policy and a data retention and disposal policy are maintained and available on request.
